# Архитектура передачи кредов: ZeroCreds ↔ запуски агентов

Дата: 2026-09-28. Статус: решение (v1), поверх
[credentials-and-secret-storage-design.md](credentials-and-secret-storage-design.md).

## Проблема

Пользователь (человек, его Claude Code, CI или веб-фронт) хочет запустить агента,
которому нужны креды: SSH к своей VM, токен Cloudflare, логин на сайт, GitHub.
Слать их в `POST /runs` вместе с задачей плохо по трём причинам:

- тело запроса оседает в логах, `run.json`, вебхуках и бэкапах, и наш API
  превращается в хранилище чужих секретов;
- если вызов генерирует LLM (Claude Code пользователя), секрет проходит через
  контекст модели ещё до того, как попадёт к нам;
- один и тот же кред нужен многим ранам, а пересылать его каждый раз значит
  плодить копии.

## Принципы

1. **Креды и работа идут разными каналами.** В запросе на работу есть только
   **ссылки** на креды, самих значений там нет.
2. **Креды поступают через одну точку входа — ZeroCreds.** Для людей это форма, для
   машин API. Всё пишется в хранилище (OpenBao) в пространство владельца, а в
   ответ приходит **хендл**.
3. **Хендл не секрет:** `cred:<owner>/<name>` (или `cred:<name>` в пространстве
   вызывающего). Его можно класть в промпт, код, лог и контекст LLM.
4. **Ран объявляет, какой кред нужен, как его доставить и куда.** Брокер выдаёт
   только перечисленное, только владельцу и только на время рана, и пишет каждую
   выдачу в аудит.
5. **Хендлы резолвятся только в пространстве владельца.** API-ключ определяет
   owner, а чужой хендл просто не находится. Так агенты разных пользователей не
   пересекаются по доступу.

## Уровни «где кред может оказаться»

| Уровень | Где кред | Как | Для чего |
|---|---|---|---|
| **L0 — прокси** | только на хосте | egress-прокси хоста подставляет заголовок в запросы к разрешённым хостам. Комната видит заглушку | HTTP API с токеном: Cloudflare, GitHub, Google, почти все SaaS |
| **L1 — агент-посредник** | на хосте; комната может **пользоваться**, но не **прочитать** | в комнату проброшен сокет ssh-agent, ключ добавлен с ограничением по хостам назначения (`ssh-add -h`, OpenSSH ≥ 8.9). Позже — короткоживущие SSH-сертификаты от нашего CA | SSH к VM пользователя |
| **L2 — в процессе комнаты, не у модели** | переменная окружения или файл для конкретной утилиты либо автозаполнение поля в браузере по команде хоста; значение маскируется в логах (G3) | CLI без поддержки прокси; логин на сайт в браузерной capability |
| **L3 — у модели** | — | **запрещено** | — |

Для L0 есть два способа подставить токен: (a) утилите подменяют base URL на
локальный шлюз (`http://sar-gw/cloudflare/…`), если она это поддерживает, —
просто и без перехвата TLS; (b) прозрачный HTTPS-прокси с CA, которому доверяет
комната, — работает с любыми утилитами, но это MITM, и держать его надо только
для хостов из списка рана.

### Частые случаи пользователя

| Кейс | Уровень | Как выглядит в запросе |
|---|---|---|
| SSH к своей VM | L1 | `{ref: "cred:vm-prod-ssh", as: "ssh", hosts: ["203.0.113.7"]}` |
| Cloudflare API / wrangler | L0 | `{ref: "cred:cloudflare", as: "proxy", hosts: ["api.cloudflare.com"]}` |
| Логин на сайт через браузер | L2 | `{ref: "cred:site-x", as: "browser-fill", hosts: ["site-x.com"]}` |
| GitHub | L0 | GitHub App на уровне брокера, отдельный кред не нужен (K5) |
| Google Drive | L0 | service account пользователя, токен на час (эпик #88) |
| Утилита, которой нужен env | L2 | `{ref: "cred:x", as: "env", name: "X_TOKEN"}` помечается в результате рана |

## Как связаны ZeroCreds и наш API: три топологии

### T1. Ссылки (основной путь, v1)

```text
1) клиент ──(форма или POST /api/credentials)──► ZeroCreds ──write-only──► OpenBao
                                   ◄── { handle: "cred:cloudflare", receipt } ──
2) клиент ──POST /runs { task, credentials: [{ref: "cred:cloudflare", as: "proxy", …}] }──► SAR
                                         SAR-брокер ──read (owner only)──► OpenBao
```

Два вызова, и у них нет общего трафика, общее только хранилище. ZeroCreds
может лишь писать, SAR — лишь читать и только пространство владельца. Хендл
переиспользуется в любом количестве ранов. Доверие здесь объяснить проще всего.

### T2. Шлюз (ZeroCreds стоит впереди, по желанию)

`POST zerocreds/api/relay/runs` принимает запрос на запуск со встроенными
значениями кредов. ZeroCreds кладёт их в хранилище как временные (TTL = ран),
подменяет на хендлы и пересылает тело в SAR. Клиенту удобно — один вызов, но
ZeroCreds тогда видит весь запрос и оказывается на пути трафика: это
доступность, задержка и более широкая поверхность доверия. Имеет смысл только
для разовых кредов, и только после T1.

### T3. Запечатанные креды (по желанию)

Клиент шифрует значение открытым ключом брокера (ключ опубликован и
закреплён в манифесте) и кладёт шифротекст прямо в `POST /runs`. Фронт SAR
его прочитать не может, расшифровывает брокер в момент доставки. Один вызов
без ZeroCreds на пути, но клиенту нужна криптография (SDK или CLI), а ключи
нужно ротировать.

### LLM-клиенты: как Claude Code передаёт кред, не видя его

Модель не должна увидеть значение ни в одной из топологий. Поэтому нужен CLI,
который читает значение **сам** и печатает только хендл:

```bash
sar cred put cloudflare --from-env CLOUDFLARE_API_TOKEN     # → cred:cloudflare
sar cred put vm-prod-ssh --from-file ~/.ssh/id_ed25519 --kind ssh --hosts 203.0.113.7
sar run --task "…" --cred cloudflare:proxy:api.cloudflare.com
```

Claude Code запускает команду, значение идёт из env или файла прямо в
ZeroCreds, а в контекст модели попадает только `cred:cloudflare`. Если у
человека кред только в голове, агент присылает ему ссылку на форму ZeroCreds
(`sar cred request cloudflare` → URL).

## Формы ZeroCreds, удобные для API

Каждая форма — это одновременно человеческая форма и машинный эндпоинт с одной
и той же схемой:

1. **Шаг 1 — спецификация формы.** `POST /api/forms` принимает поля, место
   назначения (путь в пространстве владельца) и тип креда (`token`, `ssh`,
   `login`). В ответ приходят `form_id`, URL для человека, машинный эндпоинт и
   манифест (Z1: куда именно ляжет и каким запросом).
2. **Шаг 2 — отправка.** Человек заполняет форму в браузере, машина делает
   `POST /api/forms/{id}/submit` с ключом владельца или одноразовым токеном. В
   обоих случаях приходит одна и та же подписанная квитанция с `handle`.
3. **«Скопировать как API-запрос»** прямо в форме: готовый `curl` (и
   `sar cred put …`) с той же схемой и плейсхолдерами вместо значений. Так
   форму легко подключить к себе, и Claude Code может сгенерировать весь поток
   сам.

## Карта эндпоинтов

| Кто | Эндпоинт | Что делает |
|---|---|---|
| ZeroCreds | `POST /api/forms` | создать спецификацию формы → `form_id`, URL, манифест |
| ZeroCreds | `GET /f/{form_id}` | форма для человека (с блоком «куда это уйдёт» и «скопировать как API») |
| ZeroCreds | `POST /api/forms/{id}/submit` | машинная отправка → квитанция + `handle` |
| ZeroCreds | `POST /api/credentials` | короткий путь: схема и значение одним вызовом → `handle` (только с ключом владельца) |
| SAR | `POST /runs` с `credentials: [{ref, as, hosts, name?}]` | запуск со ссылками |
| SAR | `GET /me/credentials` | мои хендлы (без значений), когда и кто их использовал |
| SAR | `GET /me/credential-access` | аудит выдач по ранам (K6) |
| SAR (событие) | вебхук `auth.required` | рану не хватает креда → ссылка на форму ZeroCreds |

## Порядок реализации

1. **Хендлы + файловый/OpenBao-бэкенд + `credentials` в `POST /runs`** с режимами
   `env` (L2, помечается) и `proxy` через base-URL-шлюз (L0). Брокер проверяет
   владельца и хосты. (K2 #46, K9)
2. **ZeroCreds: `POST /api/credentials` и `/api/forms/{id}/submit` → `handle`;
   «скопировать как API»** (Zerocreds Z9).
3. **CLI `sar`** с `cred put / request / run` (K11).
4. **SSH через ssh-agent с ограничением по хостам** (K10).
5. `AUTH_REQUIRED` с вебхуком и ссылкой (K3 #47).
6. Прозрачный HTTPS-прокси (L0b), `browser-fill` для браузерной capability (#89).
7. T2-шлюз и T3-запечатывание — только если T1 окажется неудобен.

## Как клиент убеждается, что креды обрабатываются правильно

Принцип: клиент **проверяет**, а не верит. Проверки идут в порядке убывания
независимости от нас.

| # | Проверка | Кто контролирует | Что ловит |
|---|---|---|---|
| V1 | **Аудит у провайдера.** Токены короткие и со скоупом (GitHub App на час, Google на час); всё, что они делали, видно в логах GitHub/Google/Cloudflare | провайдер | любое использование вне ранов клиента |
| V2 | **Canary-креды.** Клиент кладёт ловушку (canary token), срабатывающую при любом использовании | сторонний сервис | утечку и чтение без объявленного рана или хоста |
| V3 | **Свой vault (BYO).** Каждое наше чтение видно в аудите клиента; отзыв в его руках | клиент | чтения вне ранов, лишние чтения |
| V4 | **Self-host.** Открытый код, можно поднять у себя | клиент | всё; доверять нашей машине не нужно |
| V5 | **Квитанция рана** (подписанная): какие хендлы выданы, режим L0/L1/L2, хосты, digest образа, версия рантайма | мы, проверяемо | расхождение между объявленным и выданным |
| V6 | **Журнал выдач** с hash-chain и регулярной фиксацией в публичном репо: `GET /me/credential-access` | мы, проверяемо | переписывание истории, скрытые чтения |
| V7 | **Публичные пробы изоляции** в CI на каждый релиз («в режиме прокси значения нет в комнате») + подписанные релизы (attestation) | мы, проверяемо | регресс изоляции; подмену кода на машине |

Честная граница: root на машине SAR в момент выдачи видит значение. Её закрывают
V1–V4 и разделение машин (K8): креды живут на одной, чужой код исполняется на
другой.

## Свой vault клиента (BYO), включая российские

Клиент держит креды у себя и выдаёт нашему брокеру **только чтение конкретных
путей**. Каждое наше чтение видно в его аудите, отозвать он может в любой момент
(V3). В запуске ссылка выглядит так же, только с префиксом источника:
`cred:byo/<connection>/<path>`. Подключение к vault клиента само хранится у нас
как кред.

| Хранилище | Где | Как подключаемся | Аудит на стороне клиента | Приоритет |
|---|---|---|---|---|
| **OpenBao / HashiCorp Vault** | любое | Vault API, AppRole или JWT, политика `read` на пути | audit device | v1, один адаптер `vault` |
| **Deckhouse Stronghold** (Флант, реестр отечественного ПО, ГОСТ) | РФ, on-prem / в k8s | **тот же адаптер `vault`** — API совместим с Vault; namespaces поддерживаются | audit Stronghold | v1, проверить совместимость на стенде |
| **Yandex Lockbox** | РФ, Yandex Cloud | IAM-токен сервисного аккаунта с ролью на конкретный секрет (`lockbox.payloadViewer`) | Yandex Audit Trails (проверить, пишутся ли чтения payload как data events) | v1.5 |
| **Selectel Secrets Manager** | РФ, Selectel | REST API с Keystone-токеном проекта | уточнить | v2 |
| **Cloud.ru Secret Management** (Evolution) | РФ, Cloud.ru | REST API, разграничение доступа | уточнить | v2 |
| **Пассворк** (self-hosted, API-first, шифрование на клиенте) | РФ, у клиента | REST API; для расшифровки нужен ключ пользователя-сервиса, которого клиент заводит под нас | журнал событий Пассворка | v2, для команд без DevOps |
| 1Password, Infisical, Bitwarden | вне РФ | service accounts / machine accounts | их аудит | v2 |

Общие правила для всех коннекторов:

- мы получаем **отдельную сервисную учётку** с правом только на чтение заранее
  согласованных путей, без права на запись и листинг чужого;
- значение читается в момент доставки и не кэшируется дольше рана;
- если доступ отозван, ран получает `CREDENTIAL_REVOKED`, а не молчит;
- на каждый коннектор есть e2e-тест против стенда (Stronghold и OpenBao в
  docker, Lockbox — с тестовым облаком).
