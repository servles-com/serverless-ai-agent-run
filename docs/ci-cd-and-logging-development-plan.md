# План развития CI/CD и логов

Дата: 2026-09-27. Ограничение: **одна голая машина + GitHub**, никаких облачных
сервисов. Всё, что должно проверяться, проверяется либо в GitHub Actions
(бесплатные раннеры), либо на самой машине (self-hosted runner, systemd).

## Зачем

Код всё больше будут писать агенты (dogfood → issue → агент → PR). Значит, CI/CD —
это **гард, который не пускает мусор**, а не формальность. Он должен ловить:
сломанный код, ослабленные тесты, дыры в изоляции, регрессии поведения агентов
на реальных моделях — и не выкатывать на машину ничего, что не прошло проверки.

Логи — вторая половина того же: среда ровно настолько хороша, насколько быстро по
логам понятно, что сломалось, и насколько рано она сама об этом скажет.

## Часть 1. CI/CD: уровни гарда

```text
push/PR ─► L1 статика (GitHub, ~1 мин) ─► L2 рантайм на машине (~5 мин) ─► L3 поведение (канарейка)
                                                                             │
                           merge в main ◄── все обязательные зелёные ◄───────┘
                                │
                                ▼
         L5 CD на машине: сверка статуса коммита → blue/green → selftest → канарейка → переключение / откат
                                ▲
         L4 ночные проверки безопасности и ресурсы ───┘ (красное → issue + блок деплоя)
```

### Сейчас (есть)

- GitHub Actions `ci`: typecheck, unit (18), `bash -n` скриптов.
- `selftest.sh` на VM: failure modes (13), изоляция (11 проб), живой opencode — **руками**.
- Деплой: `gcp-lab-vm.sh bootstrap` — **руками**, без проверки статуса коммита.

### L1 — статика, на каждый push (GitHub-hosted)

| Проверка | Инструмент | Ловит |
|---|---|---|
| typecheck | tsc | уже есть |
| unit + покрытие `failures.ts` ≥ 90% | `node --test --experimental-test-coverage` | новая категория без теста |
| lint | eslint (dev-зависимость) | мёртвый код, `any`-утечки |
| shellcheck | shellcheck | баги в bootstrap/netpolicy |
| hadolint | hadolint | Dockerfile комнаты |
| секреты в диффе | gitleaks | закоммиченные токены (у нас уже были токены в чате) |
| **анти-ослабление тестов** | свой скрипт | число тестов упало; удалена проба изоляции; `assert` заменён на `console.log`; `.skip`/`.only` |
| **правило «фикс = тест»** | свой скрипт | PR меняет `src/` без изменений в `tests/` → нужна метка `no-test-needed` + объяснение |
| **чувствительные файлы** | свой скрипт + CODEOWNERS | правки `rooms.ts`, `room-network-policy.sh`, `Dockerfile`, `vm-bootstrap.sh`, `isolation.test.ts` → обязательна метка `security-reviewed` от человека |
| размер PR | свой скрипт | > 600 строк от агента → разбить |

### L2 — рантайм на реальной машине, на каждый PR (self-hosted runner)

GitHub Actions self-hosted runner на машине, отдельный пользователь `ci`
(в группе docker). Рабочий сервис не трогается:

1. checkout PR → собрать образ комнаты с тегом `sar-room-opencode:pr-<sha>`;
2. поднять **кандидатный** инстанс API: порт 8788, `SAR_DATA_DIR=/var/lib/sar-ci/<sha>`,
   тот же `runsc`, та же сеть комнат;
3. `selftest.sh` против кандидата: failure modes + изоляция (**обязательно**) +
   1 живой opencode (сначала информативно, потом обязательно);
4. артефакт CI: отчёт, `/debug` упавших ранов, хвост журнала;
5. снести кандидата и его данные.

Безопасность раннера: репо приватный, форки не запускают self-hosted джобы; джобы
раннера — только `pull_request` из веток этого репо.

### L3 — поведенческая канарейка (на PR с меткой `behavior` и каждую ночь)

Бесплатные модели шумные, поэтому гард статистический, а не «всё зелёное»:

- фиксированный набор: 6 задач × `nemotron-3-super` (самая стабильная), 2 повтора;
- сравнение с базой из `history.jsonl` за 7 дней по той же модели:
  - `SILENT_FAILURE` = 0 — жёстко (главный страх пользователя);
  - `RUNTIME_BUG`, `ROOM_START_FAILED`, `HARNESS_ERROR` = 0 — жёстко;
  - доля успехов не ниже базы минус 20 п.п.;
  - p50 длительности не хуже ×1.5;
  - новая, невиданная категория → предупреждение и issue.

### L4 — ночные проверки (таймер на машине)

- полный selftest на текущем `main`;
- **LLM red-team**: opencode на самой сильной бесплатной модели с заданием достать
  маркер соседа, ключ провайдера, достучаться до API хоста или metadata. Любая удача → P0 issue + блок деплоя;
- фазз API: огромные тела, traversal в путях артефактов и файлов, мусорный JSON, 1000 ранов в очередь;
- ресурсы: fork-бомба и OOM при 2 одновременных комнатах; **заполнение диска** (после введения квоты);
- тест перезагрузки: правила iptables и сеть комнат живы после `reboot` (раз в неделю).

### L5 — CD на машине

Деплоит **машина сама себе** и сама проверяет, что это можно деплоить:

1. таймер/вебхук: появился новый коммит в `main`;
2. **сверка статуса**: через GitHub API все обязательные проверки для этого sha зелёные.
   Иначе отказ + issue. Это главный гард: на бесплатном плане GitHub нельзя
   включить branch protection для приватного репо, поэтому последнюю линию держит машина;
3. blue/green: новый код в `/opt/sar-releases/<sha>`, кандидат на запасном порту,
   selftest против него;
4. переключение: symlink `/opt/sar` → новый релиз, `systemctl restart sar`
   (очередь ранов дожидается, осиротевшие раны корректно помечаются);
5. канарейка после деплоя: 3 живых рана; плохо → **автооткат** на предыдущий symlink + issue;
6. журнал деплоев `/var/lib/sar/deploys.jsonl` (sha, время, результат selftest, откат).

### Защита `main` без платного GitHub

- Приватный репо на Free: branch protection и rulesets недоступны. Варианты: GitHub
  Team, публичный репо (тогда защита бесплатная) или **гард на машине (L5)** +
  `scripts/merge-guard.sh` — единственный разрешённый агентам способ мёржа: проверяет
  проверки, метки, правило «фикс = тест».
- Инструкция агентам (README → Claude Code Instructions): мёрж только через `merge-guard.sh`.

### Порядок работ

| # | Задача | Размер |
|---|---|---|
| C1 | L1: shellcheck, hadolint, gitleaks, lint, покрытие | S |
| C2 | L1: анти-ослабление тестов, «фикс = тест», чувствительные файлы, размер PR | M |

## Часть 2. Логи и наблюдаемость

### Сейчас (есть)

- На каждый ран: `run.json`, `events.jsonl`, `room/{stdout,stderr}.log`, `docker-args.json`,
  `inspect.json`, `diagnosis.json`; `/runs/{id}/debug` собирает всё в один ответ.
- Журнал сервиса: строка на старт и финиш рана.
- Dogfood: `history.jsonl` + отчёты; `dogfood-status.sh`.

### Чего не хватает (найдено на живой машине)

| Пробел | Последствие |
|---|---|
| Нет индекса по ранам | «сколько `IDLE_STALL` на модели X за сутки» — только `jq` по файлам |
| Нет разбивки времени: ожидание модели vs выполнение команд | `TIMEOUT` из-за медленной модели не отличить от медленной команды (burst-находка) |
| Логи ранов без лимита размера | агент с бесконечным выводом заполнит диск |
| Секреты могут попасть в события и вебхуки | если агент напечатает ключ, он уйдёт в `events.jsonl` и наружу |
| Нет алертов | о красном selftest или `RUNTIME_BUG` узнаём, только если зайти посмотреть |
| Нет логов gVisor по упавшим ранам | падения на уровне песочницы не видны |
| Нет воспроизведения | чтобы повторить падение, запрос собирают руками |
| Ретеншн только по возрасту | при частом dogfood диск растёт |

### План

| # | Задача | Что даёт | Размер |
|---|---|---|---|
| G1 | **Индекс в sqlite** (`/var/lib/sar/index.db`): раны и ключевые события; `GET /runs?state=&category=&model=&since=` и `GET /stats` (категории, p50/p95, успех по модели/задаче) | запросы по всему парку за миллисекунды | M |
| G2 | **Тайминги шагов**: из временных меток opencode — время ожидания модели vs время tool-вызова, в `result` и в evidence `TIMEOUT` | «медленная модель» и «медленная команда» различаются сразу | S |
| G3 | **Редакция секретов**: все известные значения секретов → `***` до записи в события, логи и вебхуки + unit-тест | закрывает чеклист 3.9 | S |
| G4 | **Лимиты и ротация**: cap на stdout/stderr рана (20 МБ + маркер обрезки), ретеншн по бюджету диска (удалять старейшие успешные раньше упавших) | диск не растёт бесконтрольно | S |
| G5 | **Структурный журнал сервиса**: JSON-строки с `run_id`, уровнем и компонентом; `journalctl -o cat \| jq` | корреляция по всему пути | S |
| G6 | **Алерты в Telegram** (бот уже есть): `RUNTIME_BUG`, красный selftest/деплой, откат, диск > 80%, успех dogfood ниже порога, новая категория. Дедуп и тихие часы | среда сама говорит, что ей плохо | M |
| G7 | **Логи gVisor для упавших ранов**: `runsc --debug-log` в папку рана, хранить только при неуспехе | видны падения песочницы | S |
| G8 | **Replay**: `POST /runs/{id}/replay` — тот же запрос в новой комнате, ссылка на оригинал | воспроизведение одной командой | S |
| G9 | **Мини-дашборд** `/ui` на самом API (статика + `/stats`): последние раны, категории, модели, диск | взгляд за 5 секунд | M |
| G10 | Бэкап раноов и истории на вторую машину (rsync), когда она появится | переживает смерть машины | S |

### Порядок

G3 и G4 — первыми (безопасность и диск), потом G2 и G1 (разбор падений), G6
(алерты), G5/G7/G8, G9, G10.

## Как это связано с самоулучшением

```text
dogfood / ночные проверки ─► index + алерт ─► issue (с /debug, таймингами, логами gVisor)
        ─► агент-исполнитель ─► PR ─► L1 + L2 + L3 ─► merge-guard ─► L5 деплой с откатом
        ─► следующий dogfood подтверждает, что проблема ушла (или алерт снова)
```

Человек остаётся только в двух местах: метка `security-reviewed` на чувствительных
файлах и решение по P0 от red-team.
