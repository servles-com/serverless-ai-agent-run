# Креды и хранилище секретов без облака

Дата: 2026-09-27. Ограничения: одна голая машина, никаких облачных сервисов
(GCP/AWS), и **клиенты должны нам доверять** свои креды.

## Цепочка

```text
 пользователь ──форма──► ZeroCreds ──write-only──► хранилище секретов ──read, по рану──► брокер SAR ──► ран
 (вводит сам)            (сбор; LLM              (OpenBao на машине                      (выдаёт кред    (агент в
                          креды не видит)         или vault клиента)                      на время рана)   комнате)
```

Три разных роли с разными правами, и ни одна не видит всего:

| Роль | Что может | Чего не может |
|---|---|---|
| **ZeroCreds** (уже есть, MIT) | записать секрет пользователя по пути | прочитать его обратно (политика write-only, уже поддерживается для Vault) |
| **Хранилище** (OpenBao) | хранить зашифрованно, выдавать по политике, вести аудит каждого чтения | — |
| **Брокер SAR** | прочитать секреты **владельца рана** на время рана | читать чужие пути; писать |
| **Агент в комнате** | пользоваться кредом **через прокси**, в идеале не видя его | прочитать хранилище, получить чужой кред |

## Выбор хранилища

| Вариант | Лицензия / модель | На голой машине | Доверие клиентов | Вердикт |
|---|---|---|---|---|
| **OpenBao** | MPL-2.0, Linux Foundation (форк Vault до смены лицензии) | один бинарник, встроенное хранилище (raft/file), **static seal** — автоматическая распечатка ключом из файла, без KMS | API Vault = индустриальный стандарт; открытый код, аудит-лог | **Берём сейчас** |
| HashiCorp Vault | BSL с 2023 (не open source) | то же | бренд сильный | не берём: лицензия; API тот же, так что клиентский Vault поддержим как BYO |
| Infisical | ядро MIT; есть облако с SOC2 | нужны Postgres + Redis | хороший UX для людей, известен | как **BYO-источник** клиента позже; для себя тяжеловат |
| Bitwarden Secrets Manager | открытый код; self-host только Enterprise, MSSQL | тяжело | бренд сильный, E2EE | BYO позже |
| 1Password (service accounts / Connect) | проприетарный SaaS | не хостится | **самый сильный бренд доверия** | BYO-коннектор для клиентов, которые уже там живут |
| SOPS + age (файлы в репо/на диске) | open source | тривиально | низкое: нет аудита чтений, аренды и отзыва | только для наших собственных конфигов |
| Doppler | SaaS | — | средне | нет |

**Почему OpenBao:** умещается на одной машине без внешних сервисов; его API
совместим с Vault, поэтому ZeroCreds работает с ним без изменений (destination
`type: vault`); есть всё нужное для доверия: пути на пользователя, политики,
токены с TTL, аудит каждого обращения. Честное ограничение static seal: ключ
распечатки лежит на той же машине. Значит, шифрование защищает бэкапы и образы
диска, но **не защищает от root на машине**. Отсюда следующий принцип.

## Принципы, из-за которых клиенту можно доверять

1. **LLM не видит креды никогда.** Сбор только через ZeroCreds, агенту приходит
   `{status: "ok"}`.
2. **Агент по возможности тоже не видит креды: доставка через прокси.** Брокер на
   хосте сам подставляет кред в исходящий запрос: ключ модели через LLM-прокси,
   GitHub через git/HTTP-прокси, прочие API через egress-прокси с правилами
   «хост → какой заголовок подставить». В комнату попадает только одноразовый токен
   рана. Переменная окружения в комнате — крайний случай для CLI, которым иначе
   нельзя, и такой кред помечается в ответе рана.
3. **Короткоживущее и делегированное вместо вечного и широкого.**
   - GitHub — через **GitHub App**. Клиент ставит наше приложение на выбранные
     репозитории, мы получаем installation-токены на 1 час только на эти репо, и
     клиент отзывает доступ одним кликом, удалив приложение. Сегодня мы трижды
     упёрлись в личные PAT с правами на весь аккаунт: именно это клиенту и страшно.
   - Google и прочие — через OAuth с минимальными scope. Хранится refresh-токен,
     наружу выдаётся access-токен.
   - Всё остальное (пароли, API-ключи) — в OpenBao с TTL на выдачу и арендой на время рана.
4. **Каждое чтение видно клиенту.** Аудит OpenBao плюс наш лог «ран X прочитал кред Y
   в T, причина Z» → `GET /me/credential-access`. Клиент видит, когда и зачем брали его кред.
5. **Отзыв в руках клиента:** удалить секрет, удалить GitHub App, отозвать OAuth.
   Следующий ран получит понятную ошибку `CREDENTIAL_REVOKED`, а не упадёт молча.
6. **Разделение машин (следующий этап).** Креды и брокер — на одной машине, комнаты
   с агентами — на другой. Машина, где исполняется чужой код, никогда не хранит
   секретов. Это сильнейший аргумент доверия и ответ на ограничение static seal.
7. **Bring your own vault.** Клиент с жёсткими требованиями держит креды у себя
   (свой OpenBao/Vault, 1Password, Infisical) и даёт нам доступ только на чтение
   конкретных путей. Отозвать он может в любой момент, не спрашивая нас.
8. **Всё открыто:** SAR (публичный репо), ZeroCreds (MIT), OpenBao (MPL). Модель
   безопасности описана публично, и её можно проверить по коду.

## Сценарий «рану нужен кред, которого нет»

Возвращаем состояние `AUTH_REQUIRED`: в драфте оно было без механизма, теперь
механизм есть.

```text
POST /runs {secrets: ["github", "notion"]}
  → брокер: notion у пользователя нет
  → ран AUTH_REQUIRED, вебхук {type: "auth.required", url: <ссылка ZeroCreds>}
  → пользователь заполняет форму → ZeroCreds пишет в OpenBao users/<id>/notion
  → брокер видит секрет → ран продолжает с PREPARING
  → таймаут ожидания → FAILED / CREDENTIAL_MISSING (не молча)
```

## Этапы

| # | Задача | Размер |
|---|---|---|
| K1 | OpenBao на машине: systemd, static seal (ключ в отдельном файле `root:root 0400`), raft-хранилище, file-аудит, политики `zerocreds-writer` (create/update на `users/*`) и `sar-broker` (read), AppRole для брокера. Всё в `vm-bootstrap.sh` | M |
| K2 | Бэкенд секретов в SAR: `file` (как сейчас) \| `openbao`; секреты рана резолвятся из `users/<owner>/…`; лог доступа к кредам на ран | M |
| K3 | ZeroCreds → OpenBao: destination `type: vault` на локальный OpenBao; поток `AUTH_REQUIRED` со ссылкой в вебхуке | M |
| K4 | Egress-прокси с подстановкой кредов по хосту (GitHub, произвольные API); LLM-прокси — частный случай | L |
| K5 | GitHub App вместо PAT: установка на репо, installation-токены на 1 час, клон/push/PR через брокер | M |
| K6 | `GET /me/credential-access` и `CREDENTIAL_REVOKED` / `CREDENTIAL_MISSING` в классификаторе | S |
| K7 | BYO vault: внешний OpenBao/Vault по AppRole; затем коннекторы 1Password и Infisical | M |
| K8 | Разделение на машину кредов и машину комнат | L |

Порядок: K1 → K2 → K3 (замыкают цепочку ZeroCreds → OpenBao → SAR) → K5 (GitHub
как главный кред для сценария issue → PR) → K4 → K6 → K7 → K8.
