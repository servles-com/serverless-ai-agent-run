# План переезда trained-assist на изолированный рантайм

Дата: 2026-09-28. Первый реальный клиент North Star. Задача владельца: «уйти от
того, что агенты живут без изоляции в одной VM»
([trained-assist/trained-assist-agent](https://github.com/trained-assist/trained-assist-agent)).

Подробная карта текущего исполнения (с путями и поверхностью атаки) хранится у
владельца локально и в этот публичный репозиторий не выкладывается.

## Как сейчас (кратко)

- Сообщение из Telegram или веба попадает в `runTask`: очередь на чат, до 6
  одновременных процессов, запуск CLI (opencode по умолчанию, Claude Code или Codex)
  с отключёнными проверками прав.
- Все агенты — процессы одного unix-пользователя на одной VM. Изоляция только по
  соглашению о путях («профиль — единица изоляции»).
- Креды — файлы в домашней папке, которые при запуске превращаются в env. В
  агента уходит и серверное окружение целиком.
- MCP-серверы (skills, playwright, sibling-репо) — процессы на хосте из
  рабочих копий.
- У профиля изменяемая память: заметки, контексты, сессии, артефакты, состояние
  Playwright. Её читает и пишет каждый ран.
- Durable-планы: общая SQLite, отдельный git worktree на план, валидаторы
  запускают shell на хосте.
- Прогресс уходит в Telegram правками сообщения из stdout процесса.

## Целевое состояние

```text
Telegram/Web → trained-assist (оркестрация, сессии, доставка) ──POST /runs──► SAR на той же машине
                                                        ◄──stream / webhook──  │
                                                                               ▼
                                             комната (gVisor): агент + MCP-skills из образа
                                             /workspace  = проект/worktree рана
                                             /profile    = память профиля (только этого)
                                             креды: по ссылкам через брокер/прокси хоста
                                             к хосту: только через шлюз с токеном рана
```

Условие готовности: **на хосте не остаётся ни одного агентского процесса вне
комнаты**. Это критерий V1 из исходного драфта.

## Решения

1. **SAR ставится на ту же машину, где trained-assist.** Токены и память профилей
   уже лежат на её диске, так что переносить по сети ничего не нужно, а
   trained-assist ходит на `localhost`. Отдельная машина для комнат — позже
   (K8).
2. **Память профиля — постоянный том владельца.** Папка профиля монтируется в
   комнату как `/profile`, и никакая другая. Параллельные раны одного профиля
   работают так же, как сегодня.
3. **Свой образ комнаты `trained-assist-room`** (кастомные агенты, #77): CLI
   opencode, Claude Code и Codex, плюс skills и sibling MCP, запечатанные в образ
   по digest. Ничего не запускается с хоста.
4. **Креды только по ссылкам.** Брокер SAR читает токены профиля на хосте (файловый
   бэкенд, K2/K9) и выдаёт их по уровням L0/L1/L2 (см.
   [credential-passing-architecture](credential-passing-architecture-zerocreds-and-runs.md)).
   В комнату попадает явный allowlist env, серверное окружение — никогда.
5. **Claude OAuth.** Refresh живёт только на хосте (там уже есть брокер
   `claude-token-refresh`). В комнату уходит короткоживущий access-токен, так что
   гонки за refresh-токен не возвращаются.
6. **Обратные вызовы на хост** (cron, session, durable-tasks, RU-edge, nalog) идут
   через **шлюз хоста** с токеном рана, скоупом на профиль. `AGENT_SECRET` в
   комнату не попадает. Прямой доступ к SQLite заменяется HTTP API.
7. **Браузер** — headless Playwright внутри комнаты (capability `browser`, #89),
   `storage-state` лежит в `/profile`. Ручной логин через noVNC пока остаётся
   сервисом хоста, cookies из него сохраняются в креды профиля.
8. **Engineering worktrees**: worktree плана монтируется в `/workspace`, коммиты и
   PR делает хост (host-side PR, уже есть). Валидаторы `command_exit_zero`
   исполняются в комнате, а не на хосте.
9. **Стриминг**: правки сообщения в Telegram берутся из `GET /runs/{id}/stream`
   (#97), а не из stdout дочернего процесса.
10. **Флаг на профиль** `EXECUTION_BACKEND=local|sar`. Откат — выключить флаг.

## Этапы

| Этап | Что | Где | Готово, когда |
|---|---|---|---|
| **T0 — быстрая защита сейчас** (дни) | агенты запускаются под отдельным unix-пользователем без доступа к чужим токенам и серверному env; env по allowlist; закрыть metadata для этого пользователя; проверить права сервисного аккаунта VM | trained-assist | агент одного профиля не читает токены другого и серверный `secrets.env` (проверка тестом) |
| **T1 — возможности SAR для клиента** | `/profile`-том владельца; кастомный образ; шлюз хоста с токеном рана; allowlist env; стриминг #97; keepalive/extend-timeout; stop | SAR | e2e: ран с `/profile` и шлюзом, соседний профиль недоступен |
| **T2 — адаптер в trained-assist** | `runEngineProcess` → `sarRun` (POST /runs + stream → tg-stream) за флагом на профиль | trained-assist | один тестовый профиль целиком работает через SAR |
| **T3 — пилот** | низкорисковый поток: opencode на бесплатных моделях для 1–2 профилей владельца; сравнение ошибок и таймингов с local | оба | неделя без регрессий по метрикам SAR и trained-assist |
| **T4 — все opencode-раны**, затем Claude Code и Codex (адаптеры SAR) | | оба | ≥ 90% ранов через SAR |
| **T5 — durable-планы и engineering** | worktree в `/workspace`, host-side PR, валидаторы в комнате, durable API вместо SQLite | оба | план из 3 шагов проходит целиком в комнатах |
| **T6 — cutover** | прямой spawn выключен; Hermes, issue-fixer и прочие пути решены по одному | trained-assist | на хосте нет агентских процессов вне комнат (проверка `ps`) |

T0 делается сразу и независимо от остального: это часы работы, которые закрывают
худшее, пока идёт переезд.
