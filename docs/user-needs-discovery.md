### Что из этого следует

1. **Мультипользовательский режим переезжает из «потом» в ближайший месяц.** Нужно:
   API-ключ на пользователя (а не один общий), раны видны только владельцу, квоты
   (параллельность, время, диск), публичный HTTPS-эндпоинт. Это ровно тот
   access-control слой, который в V0 сознательно отложили, — теперь у него есть
   реальный источник требования. Делать минимально: `api_keys` → `owner` в `run.json`,
   фильтр в каждом `GET`, без tenant-неймспейсов в хранилище.
2. **Фронтенд** не должен держать мастер-токен → короткоживущие ключи / CORS.
3. **Перед первым внешним пользователем обязательны** пункты чеклиста 1.12 (квота диска),
   3.3 (LLM-прокси — ключи провайдера вне комнаты), 4.5 (SSRF вебхуков), 4.6 (rate limit).
4. **Платные модели** → BYOK: ключ пользователя хранится на сервере и подставляется
   LLM-прокси, в комнату не попадает. Сразу нужен учёт токенов/денег по рану.
5. **Кастомные агенты** → адаптер `custom`: свой образ (или команда в базовом образе) +
   контракт вывода (stdout JSON-событий или просто stdout), те же лимиты и изоляция.
6. **Тихий провал — главный враг.** `SILENT_FAILURE` должен ловиться на *реальных* ранах,
   не только в dogfood: в запросе контракт результата (`expect: {artifacts: [...], text: true}`),
   невыполненный контракт → `FAILED/EXPECTATION_NOT_MET`; плюс эвристики (агент написал
   «готово», но не было ни одной записи файла). Права агенту можно давать шире — ошибки
   «сделал не то» пользователь боится меньше.
